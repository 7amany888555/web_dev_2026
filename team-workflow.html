Working Together with Git and GitHub

A shared workflow lets many developers change the same project without overwriting each other's work.

From Your Branch to the Main Project

When you work alone, you can commit straight to main. On a team, everyone shares one repository (the project folder and its history), so you need a few extra habits: working on separate branches, keeping your copy up to date, and asking teammates to review your changes before they are added. This page walks through that process step by step.

Why Teams Need a Workflow

Fewer Collisions, Better Code

Without agreed rules, two people can edit the same file at once, someone can break the version everyone depends on, and nobody checks new code before it ships. A team workflow solves three problems:

  • Fewer conflicts. Each person works on their own branch, a separate line of development, so unfinished work never collides with someone else's.
  • Code review. Changes go through a pull request, where teammates read the code and suggest improvements before it is merged.
  • A stable main branch. main always holds working code that anyone can build on or deploy.

The Feature Branch Workflow

Eight Steps Every Change Follows

Most teams on GitHub use this cycle for every feature or fix, no matter how small.

  1. Clone the repository once to get a local copy.
  2. Create a branch from an up-to-date main for your task.
  3. Commit your work in small, clear steps.
  4. Push the branch to GitHub so others can see it.
  5. Open a pull request asking to merge your branch into main.
  6. Review: teammates comment and you push fixes to the same branch.
  7. Merge the pull request once it is approved.
  8. Delete the branch and pull the updated main.

Key Commands for Teams

Getting and Updating the Project

A remote is the copy of the repository on GitHub, usually named origin. These commands keep your local copy in sync with it.

Command: git clone

git clone https://github.com/team/project.git

Downloads the full repository and its history. Use it once, when you join a project.

Command: git pull

git pull origin main

Downloads new commits from GitHub and merges them into your current branch. Run it before you start working each day.

Command: git fetch

git fetch origin

Downloads new commits and branches but does not change your files. Use it to see what teammates did before you merge anything.

Branching and Sharing

Your Own Space to Work

Create a new branch for every task, then push it to GitHub so your team can review it.

Command: git switch -c

git switch -c feature/login-form

Creates a new branch and moves you onto it. git checkout -b does the same thing in older Git versions.

Command: git branch

git branch -a

Lists your local branches and the remote ones. The current branch is marked with an asterisk.

Command: git add and git commit

git add .
git commit -m "Add login form layout"

Stages your changes and saves them as a commit on your branch. Commit often, one idea at a time.

Command: git push -u

git push -u origin feature/login-form

Uploads your branch to GitHub. The -u flag links the two, so later you can type just git push.

Combining Work

Merge, Rebase, and Stash

While you work, main keeps moving. These commands bring those new changes into your branch, or set your own work aside for a moment.

Command: git merge

git merge main

Adds the latest main into your branch with a merge commit. It keeps the exact history and is safe on shared branches.

Command: git rebase

git rebase main

Replays your commits on top of the latest main for a straight, clean history. Only rebase branches nobody else is working on.

Command: git stash

git stash
git stash pop

Saves unfinished changes aside so you can switch branches or pull, then brings them back with pop.

Command: git log --graph

git log --oneline --graph --all

Draws every branch and how they join. Useful for seeing what teammates merged.

Merge or rebase? When in doubt, use merge. It never rewrites history, so it cannot cause problems for teammates who already pulled your branch.

Pull Requests

Asking the Team to Accept Your Changes

A pull request (PR) is a page on GitHub that shows the differences between your branch and main, with space for discussion. It is how code gets reviewed before it is merged.

  1. Push your branch, then open the repository on GitHub. Click Compare & pull request on the yellow banner, or go to the Pull requests tab and choose New pull request.
  2. Write a short title that says what the change does, such as "Add login form to homepage".
  3. In the description, explain why the change is needed, what you changed, and how a reviewer can test it.
  4. Add reviewers from the sidebar, then click Create pull request.
  5. Read every review comment, reply to it, and push fixes to the same branch. The PR updates automatically.
  6. When it is approved, click Merge pull request.

Optional: open a PR from the terminal

gh pr create --title "Add login form" --body "Adds the login form layout and validation."

The GitHub CLI (gh) opens a pull request for your current branch without leaving the terminal.

GitHub offers three ways to merge:

  • Create a merge commit keeps every commit from the branch, plus one commit that joins it to main.
  • Squash and merge combines all the branch's commits into one tidy commit. It is a good default for small features.
  • Rebase and merge places each commit on top of main one by one, without a merge commit.

Merge Conflicts

When Two People Change the Same Lines

A merge conflict happens when two branches change the same lines of a file and Git cannot decide which version to keep. Git pauses and marks the conflicting part of the file for you:

What a conflict looks like

<<<<<<< HEAD
<h1>Welcome to Our Site</h1>
=======
<h1>Welcome to the Team Site</h1>
>>>>>>> feature/new-title

The part above ======= is your version (HEAD). The part below is the version from the other branch.

  1. Run git status to see which files have conflicts.
  2. Open each file and choose the correct text: yours, theirs, or a mix of both.
  3. Delete the <<<<<<<, =======, and >>>>>>> marker lines.
  4. Stage the fixed files and commit to finish the merge.

Command: finish resolving a conflict

git add index.html
git commit -m "Resolve title conflict"

Marks the conflict as resolved and completes the merge. To cancel instead, run git merge --abort.

Team Best Practices

Habits That Keep Everyone Moving

  • Pull before you start. Update main and branch from it, so you begin with your team's latest code.
  • Keep branches small and short-lived. A pull request with a few files is reviewed faster and conflicts less.
  • Write clear commit messages. "Fix broken link on about page" helps your team; "update" does not.
  • Name branches by purpose. Use prefixes such as feature/, fix/, and docs/, for example fix/footer-spacing.
  • Never force-push to main. git push --force can delete commits your teammates already rely on.
  • Review kindly and specifically. Comment on the code, not the person, and explain why you suggest a change.
